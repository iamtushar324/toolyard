# toolyard v0.1

Status: in progress on the `t3/toolyard-v0.1` branch. This file is the contract
between the parallel work streams ("slices") that build v0.1. Each slice works
on its own branch and opens a pull request into `t3/toolyard-v0.1`; the
integration pull request `t3/toolyard-v0.1` → `main` ships them together.

## Goals

1. **Code mode, done properly.** JavaScript (QuickJS) next to Starlark, typed
   stubs, a ranked tool search (keyword and regex, optional semantic), and the
   code-mode improvements of TEC-1629.
2. **Inbox webhooks.** An agent hands toolyard a receiver; toolyard calls it
   once every approval and question of an Inbox item is answered, and for the
   other events below. Agents manage receivers through MCP tools, not only REST.
3. **Async tools.** A tool marked async returns a job at once; the agent reads
   its status or gets a callback when it ends. MCP Tasks for clients that
   support them.
4. **Rich Inbox items.** One item carries many tool approvals and many
   questions of every type, with Markdown, images, charts and a summary, and
   one decision answers them all.
5. **OAuth for MCP clients.** ChatGPT, Claude.ai, Claude Code, Cursor and
   other clients add toolyard by URL: OAuth 2.1 with dynamic registration,
   client ID metadata documents and PKCE, a consent screen, a nickname per
   client, a tool scope per client, and audit rows that name the client.
6. **High availability.** Two or more replicas on one Postgres database.
7. **Kubernetes.** A test deployment with two replicas and an in-cluster
   Postgres.

Non-goals for v0.1: replacing production's Swarm deployment, Redis or any new
infrastructure dependency, and MRTR.

## Rules for every slice

- **Both engines.** Every feature works on SQLite (one node) and on Postgres
  (many nodes). Shared tests use `internal/store/storetest`.
- **Migrations.** Add paired files with the same name under
  `internal/store/migrations/sqlite/` and `internal/store/migrations/postgres/`.
  Use only the numbers of your slice (gaps are fine; names must be unique):

  | Slice | Numbers |
  |---|---|
  | A. High availability | 0043 – 0049 |
  | B. Code mode and search | 0050 – 0054 |
  | C. OAuth for MCP clients | 0055 – 0059 |
  | D. Inbox items and webhooks | 0060 – 0064 |
  | E. Async tools | 0065 – 0069 |
  | F. Kubernetes | none |

  Never edit a migration that is on `main`.
- **Background loops.** A new loop that must run on one node at a time runs
  under `cluster.RunLeader` (below). A loop that is safe on every node (each
  row claimed with a lease) says so in a comment.
- **Caches.** A new cache that other nodes must see changes in subscribes to
  `cluster.Subscribe` and publishes with `cluster.Publish` after its write.
- **Durable work.** A row that a node executes carries `owner_instance` and
  `lease_until`, renewed while the work runs. Recovery takes only rows whose
  lease ended; it never touches another live node's rows.
- **Stateless MCP.** No feature depends on a server-initiated message reaching
  the client over the same node. Wake-ups go through the database or `cluster`.
- **Audit.** Every new path that runs a tool writes the usual audit rows.
- **Compatibility.** Existing tools, arguments, outputs, REST routes and
  tokens keep working. Starlark stays the default of `executeToolCode`;
  bk-docs skills parse its output.
- **Docs.** Update `docs/guidelines/*`, `docs/self-hosting.md` and the
  `inbox.guide` topics for what you change.
- **Verification.** CI runs the tests (`.github/workflows/inbox-integration.yml`,
  Postgres job included). Add tests next to the code.

## A. High availability (owner: slice A)

New package `internal/cluster`:

```go
package cluster

// New starts the cluster helper. On SQLite it is a single-node no-op: every
// leader lease is granted and Publish delivers in process.
func New(ctx context.Context, db *store.DB, opts Options) (*Cluster, error)

func (c *Cluster) InstanceID() string // stable for the process lifetime

// RunLeader runs fn while this process holds the named lease
// (pg_try_advisory_lock on a dedicated connection on Postgres). fn's ctx is
// cancelled when the lease is lost; RunLeader then retries until ctx ends.
func (c *Cluster) RunLeader(ctx context.Context, name string, fn func(ctx context.Context) error)

// Publish sends a small message (payload ≤ 1 KiB) to every node, this one
// included (LISTEN/NOTIFY on Postgres). Subscribe delivers it. Subscribers
// also get a periodic "resync" call so a missed message heals within the poll
// interval.
func (c *Cluster) Publish(ctx context.Context, topic, payload string) error
func (c *Cluster) Subscribe(topic string, fn func(payload string)) (cancel func())
```

Scope (from TEC-1630 and the v0.1 audit):

- Execution leases with `owner_instance` / `lease_until` for `inbox_executions`,
  `legacy_execution_claims`, `code_runs` and memory-webhook jobs; recovery only
  takes expired leases.
- Database locks (advisory locks or compare-and-set) instead of the in-process
  mutexes that guard read-modify-write: `policy.writeMu`, `inbox.submitMu`,
  `inbox.attnMu`, `oauth.userLocks`, `githubWriteMu`, the connect-t3 keyed
  mutex and the federation and upstream service mutexes where they guard
  database state.
- Single-node loops under `RunLeader`: sweepers, inbox attention, legacy sync,
  OAuth refresher, Clerk sync, retention, session purge, pricing,
  auto-approval proposer, anomaly detector, reason scorer, audit feed,
  Telegram poller, chat reconciler, events poller and retention, catalog
  refresh, memory-webhook jobs.
- Cross-node invalidation for the policy, settings, auto-approval, OAuth bearer,
  upstream configuration and catalog caches and the gateway client and
  session caches.
- Cross-node wake-ups: the realtime hub (SSE) fans out through `cluster`;
  `inbox.Wait` and the approval waiters wake on `cluster` messages and fall back
  to a database poll.
- Passkey ceremonies and the in-memory rate limits move into the database.
- `docs/self-hosting.md`: remove "never run two gateways on one database" for
  Postgres; keep it for SQLite.

Acceptance: two gateways on one Postgres in a CI test; a rolling restart of one
does not change the other's in-flight executions; a deny policy set on one is
enforced on the other within seconds.

## B. Code mode and tool search (owner: slice B)

- **JavaScript.** QuickJS compiled to WebAssembly, run by wazero (pure Go, no
  cgo) inside the existing sandboxed `codemode-worker`, with the same limits.
  `executeToolCode` gains `language` (`starlark` default, `javascript`);
  `POST /v1/code/run` accepts `text/javascript`. Script API:

  ```js
  const r = await tools.Linear.get_issue({ id: "TEC-1" }); // structuredContent, or parsed text
  const s = await tools.tryCall("Linear.get_issue", { id: "x" }); // {ok, status, result | error}
  const all = await tools.parallel([() => tools.A.x({}), () => tools.B.y({})], { limit: 4 });
  const found = await tools.search("create a linear issue", { mode: "keyword", limit: 5 });
  console.log("...");            // user output
  return { summary: "..." };      // the result
  ```

- **Typed stubs.** `servers/<Server>/<tool>.d.ts` (JavaScript) next to the
  existing `.pyi` (Starlark), generated from the input and output schemas, plus
  `servers/index.d.ts`. Prefer `structuredContent` for results.
- **Tool search** (new package `internal/toolsearch`), one engine used by the
  MCP tool `tools.search`, the REST route `GET /v1/code/search`, and scripts:
  - `keyword`: BM25 over the tool name, description, parameter names and
    parameter descriptions, with field weights.
  - `regex`: RE2, at most 200 characters, over the same fields.
  - `semantic`: optional. Embeddings from an OpenAI-compatible endpoint
    (`-embeddings-url`, `-embeddings-model`, key from the credentials folder),
    cached per tool and schema hash. Off unless configured. `auto` fuses
    keyword and semantic with reciprocal rank fusion when semantic is on.
  - Detail levels: `name`, `summary`, `full` (with schemas). Results are scoped
    to the caller (`CatalogFor`).
- **TEC-1629:** `echo` option (`full` default on MCP, `preview`, `none`) with an
  output budget reserved for user prints and the result; a per-agent cap with a
  fair queue next to the global cap; `try_call` for Starlark; a bounded
  `parallel` for Starlark; a `run_id` on outer and nested audit rows.

## C. OAuth for MCP clients (owner: slice C)

- toolyard becomes an OAuth 2.1 authorization server for its own `/mcp`:
  - `/.well-known/oauth-protected-resource` (RFC 9728) and
    `/.well-known/oauth-authorization-server` (RFC 8414); the 404 block for
    these paths in `cmd/gateway/main.go` goes.
  - `POST /oauth/register` (RFC 7591), client ID metadata documents
    (`client_id_metadata_document_supported: true`), `GET /oauth/authorize`
    with PKCE S256 required and the `resource` parameter (RFC 8707),
    `POST /oauth/token` (`authorization_code`, `refresh_token` with rotation
    and reuse detection), `POST /oauth/revoke`.
  - A 401 from `/mcp` carries
    `WWW-Authenticate: Bearer resource_metadata="<public-url>/.well-known/oauth-protected-resource"`.
- **Consent.** The signed-in person sees the client's name, redirect host and
  requested access, sets a nickname, and chooses the tool scope (everything they
  can use, or chosen servers and tools, with denies) before they allow it.
- **Identity.** Each authorization becomes an agent owned by that person
  (`kind = oauth_client`). Audit rows carry the agent, the nickname and the
  OAuth client id. Static agent tokens keep working.
- **Per-agent scope.** A new per-agent allow and deny list, applied on top of
  the owner's scope in `internal/access` and in `CatalogFor`, for OAuth clients
  and for ordinary agents.
- **Dashboard.** A "Connected apps" page: nickname, client, scope, last used,
  rename, change scope, revoke, link to its audit rows.
- **Docs.** How to add toolyard to ChatGPT (developer mode connector),
  Claude.ai (custom connector), Claude Code, Codex and Cursor.

## D. Inbox items and webhooks (owner: slice D)

- **Rich items** (schema version 3, versions 1 and 2 still accepted):
  `tools[]` up to 50 calls, `questions[]` up to 20, `attachments[]` up to 24, in
  one item. `message` is Markdown (CommonMark and GitHub tables, sanitized, no
  raw HTML). One decision answers every call and every question.
- **Question types:** `free_text`, `single_choice`, `multiple_choice`,
  `yes_no`, `number` (min, max, step, unit), `date`, `datetime`, `scale` (1 to
  N with end labels), `ranking` (order the options). Each question has `id`,
  `required`, and an optional `default` and `recommended`.
- **Charts:** `line`, `bar`, `stacked_bar`, `area`, `pie`, `scatter`, drawn by
  the dashboard's own SVG renderer (no external library).
- **Webhooks:** MCP tools `callbacks.register`, `callbacks.list`,
  `callbacks.update` (disable, rotate, remove), `callbacks.set_default` (the
  receiver used when an Inbox call omits `callback_ref`) and `callbacks.test`.
  Events: `inbox.decision` (the item is fully answered; unchanged shape plus
  the new answers), `inbox.expired`, `inbox.cancelled`, `execution.completed`
  (a granted call ran, with its outcome), `approval.decided` and
  `approval.executed` (legacy deferred approvals), `ping`, and the job events of
  slice E. A generic emitter for the other slices:

  ```go
  // EmitForAgentTx queues one event for one of agentID's receivers inside tx
  // (at-least-once, signed, retried). ref "" is the agent's default receiver
  // (read through tx; none: nil). A ref that is not an active receiver of
  // agentID returns ErrReceiver. A receiver that did not opt into eventType
  // (its events list) gets nothing.
  func (s *Service) EmitForAgentTx(ctx context.Context, tx *sql.Tx, agentID, ref, eventType string, data any) error
  ```

  `tx` is a `*sql.Tx` of the store (there is no `store.Tx`). Several receivers
  may follow one request. A receiver gets only the event types it registered
  for (default: the three `inbox.*` types) and the version 3 decision shape
  only with `v3: true`.

## E. Async tools (owner: slice E)

- An administrator marks an upstream server or a tool async (or async after a
  given time). A call to it starts a durable job and returns at once:
  - to a client that declared MCP Tasks (mcp-go's task hooks), a task;
  - to other clients, `{job_id, status, poll: "jobs.status"}`.
- Tools `jobs.status`, `jobs.result`, `jobs.wait` (up to 60 s), `jobs.cancel`
  and `jobs.list`; REST `/v1/jobs/...`; the reserved argument `_callback_ref`
  (like `_reason`) asks for a `job.completed` / `job.failed` callback.
- Jobs carry leases (rule above), store large results through the blob store,
  record upstream progress notifications, and are kept 7 days.
- Code mode can start a job and wait for it.

## F. Kubernetes test deployment (owner: slice F)

- `deploy/k8s/overlays/ha-test/`: two toolyard replicas with RollingUpdate
  (`maxUnavailable: 0`), a PodDisruptionBudget, preferred spreading across
  nodes, a Postgres 16 StatefulSet with a persistent volume, a migration Job,
  an Ingress, NetworkPolicies, and configuration through patches. Cluster
  specifics (host name, node selector, storage class) are inputs, not
  committed values.
- `scripts/k8s-test-deploy.sh`: apply, migrate, wait for the rollout, smoke
  test (health, readiness on both pods, MCP `server/discover`, a code-mode run).
- CI pushes an image for each pull request from this repository (not forks),
  tagged `pr-<number>-<sha>`, so a branch can run in the cluster before merge.
- `deploy/k8s/README.md` explains both the single-replica base and the HA
  overlay.
